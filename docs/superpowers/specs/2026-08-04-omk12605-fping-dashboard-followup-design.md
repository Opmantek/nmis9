# OMK-12605 follow-up: fping-owned events don't refresh or reach the dashboard file

Date: 2026-08-04
Ticket: OMK-12605 (follow-up to the operational event status documents work)
Status: implemented and reviewed (nine independent review rounds, all findings fixed except the accepted limitations recorded below). This document's original "proposed, pending team review" framing below describes the design as it was pitched before implementation — see the code and the "Known limitations" section near the end for what actually shipped and what remains open.

## Summary

The operational status document work (8 tasks, already implemented and reviewed) delivers correctly for every event that's checked directly inside a node's own `collect()`/`update()` cycle: Interface Down, SNMP Down, WMI Down, Service Down, and custom model alerts. Node Polling Failover mostly fits this pattern too (see the round 5 correction below for the one node subset that didn't, since fixed). Two specific events — **Node Down** and **Backup Host Down** — are handled by a separate background process (the fping worker) that only acts on state *transitions*, not on every cycle. That mismatch causes two concrete problems, both traced to actual code during a final whole-branch review, not theoretical. Backup Host Down is one of the two events this entire ticket exists to expose in the dashboard file — so this follow-up is not a polish item, it's a gap in the ticket's core deliverable.

This document describes both problems, why they happen, and the fix proposed to close them. Nothing has been implemented yet — this is for team review before that work starts.

## Background

NMIS9 writes MongoDB "status" documents (`ok`/`error`, refreshed every poll) for threshold checks and model alerts, but historically never for ordinary code-raised events like Node Down or Interface Down. The base OMK-12605 work added a third writer (`method: Operational`) by hooking into `notify()` (raises/refreshes an `error` doc) and `checkEvent()` (raises/refreshes an `ok` doc) — the two functions that already handle event bookkeeping everywhere in the codebase. Because most callers of `notify`/`checkEvent` run every single poll cycle regardless of whether anything changed, the status documents refresh automatically, with no changes needed at any call site.

That assumption — "these functions get called every cycle" — was true before this ticket too, in the sense that nothing needed it to be true. `notify`/`checkEvent`'s original job, before this ticket, was purely event bookkeeping: create or update an event record, decide severity, decide whether to log or escalate. The new status-document feature rides on top of that existing call pattern rather than replacing it — and it holds everywhere that pattern was already "call every cycle regardless." It does not hold in the one place that pattern was never built that way.

## The two problems

### Problem 1: Node Down and Backup Host Down don't refresh, and a never-down node gets no entry at all

Node Down, Backup Host Down, and the failover event are raised by a *separate background process*, the fping worker (`bin/nmisd`), not by `collect()`. That worker is deliberately fast and lightweight — it exists so an outage is detected within about a minute, instead of waiting for the next full (heavier, less frequent) SNMP poll cycle. To do that cheaply, it only calls `notify`/`checkEvent` when the state actually **changes**:

- Raising: `bin/nmisd:3090`, `if (!$event->exists || $down_status_in_catchall ne 'true')`
- Clearing: `bin/nmisd:3147`, `if ($event->exists && $event->active)`

Both are transition gates, not per-cycle checks. This is correct and deliberate for the fping worker's actual job — nobody wants a "Node Down" event logged and escalated again every minute while an outage continues. The gap is that the new status-document feature was built assuming this call pattern behaves the same way everywhere `notify`/`checkEvent` are used, and it doesn't.

Consequences, verified directly against the code:

- **While a condition persists, its status document is never refreshed.** Written once at the moment of transition, then untouched until the condition clears. These documents are correctly exempt from the routine 500-second staleness sweep (Task 5 of the base work), but still subject to the normal 24-hour expiry. A node down, or running on backup, for longer than 24 hours has its status document silently expire, even though the condition is still real.
- **A node that has never once gone down never gets an entry at all.** The "clear" branch only runs when there's an existing active event to clear (`bin/nmisd:3147`). A permanently healthy node never has one, so `checkEvent` is never called for it, so no `ok` document is ever created — unlike every other event type in this feature, where a healthy check produces an `ok` entry from its first poll.

**Correction — note on `bin/nmisd`'s interaction with Backup Host Down, added during the final whole-plan review.** The paragraph above, and the raising/clearing gate description just before it, are accurate for Node Down and for Backup Host Down's *code path*. But a whole-plan review traced `bin/nmisd`'s raise gate (`bin/nmisd:3084-3090`: `if (!$event->exists || $down_status_in_catchall ne 'true')`, where `$down_status_in_catchall = $catchall_data->{"${whatevent}down"}`) specifically for the backup case, and found that before this follow-up plan, nothing ever wrote a `backupdown` catchall flag at all — the flag-writing regex in `handle_down` only covered `snmp|wmi|node`. That means `$down_status_in_catchall` was always `undef` for Backup Host Down, and in Perl `undef ne 'true'` is always true — so the raise gate was **always open**, and `bin/nmisd` was calling `notify()` for Backup Host Down on every single fping cycle while a backup was down, not just on transition, contrary to how the gate is described working above.

Two practical implications follow from this, both re-verified directly against the code:

1. `bin/nmisd`'s *code* is genuinely untouched by this follow-up (still true, see "What stays untouched" below) — but its *runtime behavior* for the backup path does change as a side effect of Task 2 populating `backupdown` correctly. Once that flag is written, the raise gate starts closing after the first down cycle, matching how Node Down already behaved, instead of staying permanently open. This is a beneficial side effect — it stops needless per-cycle event re-raising/re-logging for a condition that hasn't changed — not a regression. It should be stated plainly rather than left implied by "nothing changes here."
2. This also means the *refresh-cadence* half of Problem 1, as originally written above, did not actually apply to Backup Host Down's down-state the way described — its status document (once such a thing existed) would already have been refreshing every fping cycle, just via this latent gate-always-open quirk, not by design. The two things that genuinely still needed fixing for Backup Host Down were: (a) a permanently healthy node never getting an `ok` entry at all (the gate only opens when something needs raising, never fires for "nothing to raise" — this part of Problem 1 is unaffected by the correction above and still applies in full), and (b) the dashboard-file visibility gap (Problem 2). Both remain correctly diagnosed and are the real reasons this event needed the fix.

### Problem 2: dashboard-file visibility is broader than just fping — it's a structural gap, not an fping-specific one

The per-node dashboard file is only ever assembled and written by `collect()`/`update()`, using a "push" model: each keeps a scratch in-memory structure (`dashnode_context`) alive for the duration of one call, and any status-document save that happens *while that structure exists* gets automatically mirrored into it. At the end of the call, that structure is flushed to the JSON file.

The fping worker is a **different operating system process**, and its throwaway `$nmisng` object was never set up through `load_dashnode_data`, so it has no `dashnode_context` to be mirrored into. The write to MongoDB still succeeds — it's a correct, real document — the file simply has no way of learning it happened.

This turns out not to be unique to fping. Checked directly: **`services` can also run as its own independently-scheduled job** (`lib/NMISNG/Node.pm:8199`, `sub services`), completely separate from a `collect()` run, and it never calls `load_dashnode_data`/`save_dashnode_data` either. So Service Down/Service Degraded can hit this same visibility gap on any site that schedules services checks on their own cadence rather than folded into `collect()`. The difference: `collect_services()` itself re-evaluates and calls `checkEvent`/`notify` fresh every time it runs regardless of schedule (`lib/NMISNG/Node.pm:9126-9199`), so services never has Problem 1's refresh/staleness issue — only this visibility gap, and only when scheduled standalone. This document's fix targets the fping case specifically, since that's the customer-facing gap; the services case is noted here as a structurally identical, separately-triggered instance worth its own follow-up if it's confirmed to occur in practice.

## Proposed solution

Extend `collect()`'s existing per-cycle work, rather than changing the fping worker or adding a new database read at file-write time.

### Why not modify the fping worker, and why not query the database at write time

Two alternatives were considered and set aside:

1. **Decouple the fping worker's status write from its transition gate**, so it refreshes MongoDB every cycle regardless of state change. This would fix the refresh/staleness half of Problem 1, but does nothing for Problem 2 — the write still happens in a process with no `dashnode_context`, so the file still never sees it.
2. **Query MongoDB for current status at the moment the dashboard file is written**, replacing the in-memory push with a direct read. This would fix Problem 2 in general, but adds a new database read to every `collect()`/`update()` call — and the dashboard file has a standing resource constraint from the original requirements: **dashnode file read/write must stay under 10% of overall resource use.** Adding a new per-cycle query for this is exactly the kind of cost that constraint was meant to guard against, and it's avoidable.

### The actual proposal: give `collect()` what it needs, using data it already has

`collect()` already reads everything required to know the current node/backup state, every cycle, regardless of whether the fping worker owns the down/up decision:

- **Node Down**: the catchall already carries a `nodedown` flag, kept current by `handle_down` (`lib/NMISNG/Node.pm:2166-2176`) whichever process last updated it. `collect()` can read this flag directly — no new query, no new computation.
- **Backup Host Down**: `pingable()` already reads the cached fping ping data every cycle regardless of who owns the decision, and already determines whether it's using the primary or the backup host's numbers, as part of its existing logic (`lib/NMISNG/Node.pm:1966-1977`). That's exactly the signal needed — it's already sitting in memory during `collect()`'s normal run, at zero extra cost.

The fix: inside `collect()`'s existing per-cycle pass, add a step that writes/refreshes the operational status document for these events using this already-available data, independent of whatever the fping worker decides to do with the actual event (raise, clear, log, escalate) on its own faster schedule. Because this write happens *inside* `collect()`, the existing `dashnode_context` push mechanism (already built by the base OMK-12605 work) picks it up automatically — the same mechanism Interface Down and SNMP Down already rely on. No change to `bin/nmisd`. No new database query.

**Precise anchor:** `pingable()` (`lib/NMISNG/Node.pm:1911-2114`) has a block shaped `if ($mustping) { ...calls handle_down... }` at lines 2018-2092 — this only runs when fping's cached data is missing or stale (`collect()` falls back to pinging and owning events itself in that case). When `$mustping` is false — fping owns the decision, the normal case — that block currently does nothing at all for events or status. The fix is a paired `else` alongside it: when fping owns the decision, don't touch the event, but still refresh the status document from data already in scope (`$catchall_data->{nodedown}`, already a live reference via `data_live()` at line 1920; and, for Backup Host Down, the primary-vs-backup values already read at lines 1966-1977, which will need a small new tracking variable — the existing code overwrites `$ping_loss` etc. in place when it switches to backup numbers, without recording *that it switched*, so a boolean like `$used_backup` needs to be set alongside that overwrite for the new step to read).

**What the new step calls:** `NMISNG::Status::save_operational_status`/`close_operational_status` directly — *not* the full `notify()`/`checkEvent()`. Those can create or rename event records, which must stay the fping worker's exclusive responsibility; the status-document helpers only ever touch the status collection, so `collect()` and the fping worker can run independently on their own schedules without ever conflicting over event ownership.

### What stays untouched

- The fping worker's transition-gated event raising/clearing, logging, and escalation — unchanged. Outage detection stays on its fast, roughly one-minute cadence.
- The dashboard file's existing push-based assembly mechanism — unchanged. This fix uses it, rather than replacing it with a pull.

### The one honest trade-off

Status-document freshness for these two events now follows `collect()`'s cadence (typically a few minutes) rather than fping's faster cadence (roughly a minute). The actual up/down *decision*, logging, and escalation are unaffected by this — they remain exactly as fast as they are today. A document refreshing every few minutes is far inside the 24-hour TTL window that was the original concern, so this doesn't reopen the staleness problem; it just means the document's timestamp granularity matches `collect()`'s cycle rather than fping's.

### Why this is sufficient

- Refresh: solved — `collect()` writes the current true state every time it runs, regardless of whether a transition happened.
- Never-down node with no entry: solved — the same per-cycle write creates the `ok` entry from the node's first `collect()` cycle, the same way Interface Down already works.
- Dashboard-file visibility: solved — the write happens inside the same process that already owns `dashnode_context`, so it's picked up for free.
- Resource budget: respected — no new database *reads* beyond what `collect()` already does each cycle (verified: no new queries appear anywhere in the diff). This does add one status-document upsert *write* per node per collect cycle (two for multihomed nodes, since Node Down and Backup Host Down are separate writes) — a marginal, expected cost inherent to the feature, comparable to what threshold/interface status docs already cost, not a problem the resource-budget constraint above was aimed at. The original "no new reads or writes" phrasing overstated this; corrected here during the final whole-plan review.

## Explicitly out of scope for this document

- **The `services`-as-standalone-job visibility gap** noted above. Same underlying pattern, but not customer-facing today the way Backup Host Down is, and deserves its own confirmation of whether any site actually schedules it that way before committing to a fix.
- ~~The separate Events.nmis upgrade-propagation issue~~, a second Critical finding from the same final review: the config defaults added in the base work (`Status => false` on a few events) can't reach a customer who already has their own `conf/Events.nmis`, because the install/upgrade tooling only auto-merges `Config.nmis` — every other config file is diffed for manual review, never auto-applied. That's an installer/deployment question, unrelated to the code paths discussed here, and needs its own separate decision. **Resolved after round 5** (see the "round 6" note in Known limitations below): `installer_hooks/10-postcopy-confmerges` now runs the same merge against `Events.nmis` too.

## Known limitations (recorded after nine rounds of independent review)

This work went through nine rounds of independent, "blind" review (fresh reviewers each time, no visibility into prior findings or each other). Every Critical and Important finding across all rounds was fixed and re-verified, including several real bugs in the fixes themselves — most notably, `Backup Host Down`'s up/down decision went through two iterations before settling on deriving it from live ping data on *both* of `pingable()`'s code paths (not just the fping-owned one), the same way `Node Down` already does, after review found the intermediate versions could either get permanently stuck on a stale flag or falsely report "down" whenever the backup simply hadn't been measured that cycle. Round 5 found and fixed three further issues: `Node Polling Failover` was missing this same both-code-paths refresh for ping-only multihomed nodes (see the correction note earlier in this document); the status-document identity used for upserts didn't include `method`, so a same-named custom threshold or alert could be silently overwritten by an operational-status write; and `checkEvent()` wrote its "ok" status document before confirming the underlying event actually closed, which could show a false all-clear when the close itself failed (the pre-existing OMK-12622 duplicate-key case). The following items were deliberately left as accepted limitations rather than fixed, because each is either genuinely out of this scope, needs a decision this document can't make on its own, or costs more to fix than the risk it carries.

1. ~~Health percentages do change on some nodes upgrading with default config, contrary to the base spec's Goal 4.~~ **Resolved in round 5** with a new master gate, `health_score_include_operational_events` (`conf-default/Config.nmis`, default `'false'`, wired into `compute_thresholds`'s Operational-doc branch in `lib/NMISNG.pm`). Off by default, no `method => "Operational"` document counts toward `status_summary` at all — an existing customer's health numbers stay exactly as they were before this ticket, with nothing in their network having changed. The documents themselves still write, still appear in the status collection and the dashnode file (the ticket's actual goal), they simply don't move the percentage until a site turns this on. Once on, the finer-grained per-event `Status` flag and `status_summary_exclude_events` list described below still apply exactly as before. This was originally raised as needing a product decision because "always count" and "never count" both had a real customer on each side; the gate turns that from a single global decision into a per-site one, so no one decision has to be right for everybody.
2. ~~`Config.nmis`'s `status_summary_exclude_events` and `conf-default/Events.nmis`'s per-event `Status` flags disagree for two events.~~ **Resolved, also in round 6 — revised after the final whole-branch review.** Both events already agreed with `Events.nmis`, not with the exclude list: `Service Configuration Error` ships `Status => 'true'` explicitly, `Model File Invalid` has no entry of its own and falls back to `Default`, which also ships `Status => 'true'`. Unlike `Interface Down`/`Service Down`/`Service Degraded` (documented, deliberate exclusions — see the base spec), no rationale for excluding either of these two was ever written down; the mismatch looked like an oversight, not a considered decision. Both were initially removed from the shipped `status_summary_exclude_events` default. The final review then found a real, pre-existing reason `Service Configuration Error` specifically needs to stay excluded: `lib/NMISNG/Node.pm` (~8836-8850, ~9372-9385) never revisits this event if the underlying misconfiguration is fixed by removing the bad service reference rather than fixing the Services table, so it can get stuck active forever — which would now permanently degrade a node's health for a problem already believed fixed. `Service Configuration Error` was put back on the exclude list for that reason; `Model File Invalid` has no such risk (it's re-checked fresh every single cycle regardless of any list) and stays removed. A site that wants either excluded/included differently can still edit their own `Config.nmis` list; nothing about that mechanism changed, only the shipped default. Test: `test/t_operational_status.pl` Fix 13 (proves both directions).
3. **`status_summary_exclude_events` intentionally still exists, and was considered for removal in round 6 but kept.** Once `Events.nmis` became installer-mergeable (round 6, below), the question was raised whether this list is now fully redundant with `Events.nmis`'s own per-event `Status` flag. It isn't: `Interface Down`, `Service Down`, and `Service Degraded` ship `Status => 'false'` in `Events.nmis` as a *permanent* design choice (per the base spec: "these do not affect node state today"), not merely an upgrade-safety patch — and every existing customer's live `Events.nmis` already has the old `Status => 'true'` for these (an existing key, so the merge tool can never flip it). Removing the list would mean any site that turns `health_score_include_operational_events` on would also silently start counting these three toward node health, with no dedicated way to turn that back off short of manually editing `Events.nmis` per event. Kept for that reason: it protects a real, ongoing design intent for a narrower, opt-in population, not just the same upgrade-safety concern the master gate already covers.
4. **Any event name not known in advance defaults to counting toward node health.** `save_operational_status` falls back to `$events_config->{'Default'}`, which ships `Status => 'true'`. Any site raising custom code-raised events from a plugin or integration will see those events counted unless explicitly added to the exclude list. This is the general case of limitation 2's `Model File Invalid` example; no fixed list can close it for names that don't exist yet.
5. **The added database-write volume and dashboard-file size have never been measured against the original "under 10% of overall resource use" constraint.** `checkEvent` now writes a status document on every call, which is once per collected interface per node per cycle, plus once per service. This is an increase on an existing cost (threshold documents already scale with interface count) rather than a new class of load, but nobody has put a number on it for an interface-heavy node. Needs a measurement on a representative site before this reaches one, not a code change.
6. ~~`dashnode_context` accumulates in background processes that never flush it.~~ **Resolved in round 6.** `Status::update_dashnode_data` now checks `defined($self->nmisng->{dashnode_context})`/`{data}` before mirroring anything in — a process that never called `load_dashnode_data` (the fping worker, standalone `services`/`thresholds` jobs) simply has nothing to mirror into, so nothing accumulates there. The status document itself still writes normally either way; only the in-memory dashboard mirror is skipped. Test: `test/t_operational_status.pl` Fix 12, proving both the no-op case and that the normal mirror still works once something in the same process has genuinely called `load_dashnode_data`.
7. **A brief, self-correcting false "ok" is possible from the `Event->delete` close hook.** If escalation cleanup deletes an old, already-inactive event record for unrelated housekeeping reasons, the close hook can flip a currently-`error` status document to `ok` for up to one poll cycle before the next real check corrects it. The base spec already accepts a version of this trade-off explicitly ("worst case is a brief truthful flap"); recorded here again because a later review specifically named it. **Round 8 addition**: this same close hook (`close_operational_status`) writes directly to the status collection and does not refresh the dashboard JSON file or the record's expiry timer. For a node still being polled, the next cycle's normal write repairs both, same as any other update. For a node that stops being polled shortly after an out-of-band close, the dashboard JSON file (which has no expiry mechanism of its own) simply keeps whatever it last had indefinitely, until some future poll cycle overwrites it — not tied to the Mongo record's own 24-hour TTL, a separate lifecycle from it. Not fixed, since doing so would mean adding a new database read into GUI/API request processes that were deliberately kept free of the dashboard-file machinery.

**Round 9 correction**: an earlier version of this note argued the gap doesn't matter for compliance because the `events` collection "retains closed events as historic records" independently. Checked directly and that's wrong under default settings: `keep_event_history` ships `'false'` (`conf-default/Config.nmis`), and with that default `Event::delete()` (`lib/NMISNG/Event.pm` ~531) hard-removes the record rather than marking it historic — the 7-day retention only applies if a site opts in. The specific out-of-band path this item is about (`Events::eventDelete`, the API-delete route) is also explicitly documented in its own code comment as not writing to the durable flat-file event log the normal close path uses. So an out-of-band delete under default settings leaves less trace than previously stated here. This doesn't change the "don't fix in code" conclusion, though: the `status` collection was never a retention mechanism regardless of this bug, it's capped at a 24-hour TTL by design either way, so fixing `close_operational_status()` would add no audit/compliance value. What this correction does surface is a genuinely separate, pre-existing gap in NMIS9's own event-deletion logging (unrelated to code this ticket touches, and out of this ticket's scope) — worth its own ticket if retention/audit of manually-deleted events ever matters to a customer.
8. **This document and the base spec are not fully up to date with everything that shipped.** Both still describe some intermediate designs (an earlier catchall-flag-based approach for `Backup Host Down` in particular) rather than the final, live-ping-data-only mechanism both events now share. The code and its tests are the authoritative source for exact current behavior; this document explains the reasoning and the journey, not a live specification.
9. **Removing `host_backup` from a node leaves its last `Backup Host Down` document exactly as it was, error or ok, rather than clearing it.** Found during physical testing: once `host_backup` is unset, `pingable()` has nothing left to check, so it correctly stops writing anything for that event at all, but it doesn't go back and retract what it already wrote. An existing `error` document sits there, still counted toward health if the master gate is on, until it naturally expires (`purge_status_after`, default 24h). Consistent with the same principle used everywhere else in this design ("never assert a state about a condition nothing assessed" applies to *clearing* too, not just to raising) but not obvious to someone who just removed a backup address expecting the alert to go away immediately. Not fixed, same reasoning as the rest of this section: no code change is worth adding a "did this specific field just get unset" special case for.

## Round 6: Events.nmis becomes installer-mergeable, one gate removed

After five rounds of review, a separate design conversation (not a review round) revisited why this ticket needed two site-wide Config.nmis list-gates (`operational_status_untracked_events`, `status_summary_exclude_events`) in the first place: `Events.nmis` never auto-merges into an existing install, so a per-event flag added there wouldn't reach anyone already running NMIS9.

`admin/updateconfig.pl` (the tool that already auto-merges `Config.nmis` on upgrade) turned out to be generic already — it recursively adds only missing keys at any depth, in any two same-shaped nested hashes, and never touches a key that's already present. It was never Config.nmis-specific, just never invoked against anything else. `installer_hooks/10-postcopy-confmerges` now also runs it against `Events.nmis`, so a genuinely new per-event flag (like `TrackStatus`) now reaches every existing install automatically, the same as `Config.nmis` keys always have. Verified directly (`test/t_updateconfig.pl`): a missing top-level event entry is added wholesale, a missing key inside an existing entry is added without touching that entry's other values, and a site's own customizations to existing keys always survive.

This made `operational_status_untracked_events` genuinely redundant — it only ever protected one event (`Planned Outage Open`), via a brand-new key (`TrackStatus`) with nothing pre-existing to conflict with — so it was removed from `Config.nmis`, along with its consuming check and helper in `lib/NMISNG/Status.pm`. `TrackStatus` in `Events.nmis` is now the sole gate for "should a status document be written for this event at all."

`status_summary_exclude_events` was also considered for removal on the same grounds, and deliberately kept — see limitation 3 above for why it isn't the same kind of redundancy.

Also picked up in this round: the `update_dashnode_data` guard that limitation 6 had flagged as designed-but-not-applied. Applied — see limitation 6 above.

And: `Service Configuration Error` and `Model File Invalid` removed from the shipped `status_summary_exclude_events` default, resolving limitation 2 — see there for the reasoning (and its revision after the final review, below).

### Final whole-branch review, before merge

Two independent reviewers did one last pass over the complete diff against `nmis9_dev` (not incremental — the full ~4,150-line change), specifically checking whether six-plus rounds of incremental fixes still hang together as a coherent whole. Both came back clean on correctness; one found three things worth fixing, none of them Critical or Important:

- **`Service Configuration Error` put back on `status_summary_exclude_events`**, reversing half of the change described in limitation 2 above — see there for why.
- **A stale comment in `lib/NMISNG.pm`** justified keeping the exclude list by "Events.nmis is not auto-merged", which stopped being true once the installer started merging it. Corrected.
- **`enable_dashnode_file` added to `conf-default/Config.nmis` and `Table-Config.nmis`, default `'false'`.** Pre-existing gap, unrelated to this ticket's own code: this setting (which turns on the entire per-node dashboard JSON file) was read by several functions but never shipped anywhere or listed in the GUI config table, so a site had no discoverable way to turn on the very feature this ticket's follow-up half is about, short of hand-adding the exact key name. `getbool(undef)` was already false, so this changes no behavior, only makes the setting discoverable.

### Round 7 re-review: the installer merge line itself had a bug

Two independent reviewers re-reviewed the round-6 delta and both flagged the same line: the unconditional `Events.nmis` merge added to `installer_hooks/10-postcopy-confmerges`.

**The bug, confirmed against the code**: `05-postcopy-configfiles` only ever copies `Config.nmis`, `users.dat`, and `performance.nmis` into a fresh install's `conf/` — `Events.nmis` is deliberately never provisioned there, so a large population of sites (anyone who never customized it) has no `conf/Events.nmis` at all, and `NMISNG::Util::loadTable` reads `conf-default/Events.nmis` directly, live, on every single load for them. The unconditional merge line, on such a site's first upgrade with this branch, would have `admin/updateconfig.pl` auto-create a full copy of `conf-default/Events.nmis` (its own fallback for a missing live file starts from an empty hash, so every template key reads as "missing" and gets copied wholesale). From that point on: any *future* NMIS release that changes an *existing* value in `conf-default/Events.nmis` would never reach that site again (the merge only adds genuinely missing keys), and every later upgrade would flag the new file as "custom, needs manual review" for a file the admin never touched. Exactly backwards from the goal — sites with no customization didn't need merging at all, they were already getting live updates for free.

**Fixed**: the merge now only runs `if [ -f "$TARGETDIR/conf/Events.nmis" ]`. A site with no live copy is left exactly as before; a site that already has one still gets the additive merge (new/missing per-event keys, e.g. `TrackStatus`, without touching anything the site already has).

**A second, related, un-coded-around finding — resurrecting deliberately deleted event entries.** Separately: a site that *does* have its own `conf/Events.nmis` and deliberately deleted a whole event entry (a supported way to route that event to `Events.nmis`'s own `Default` fallback) will have that entry silently re-added by the merge on the next upgrade, since `admin/updateconfig.pl` can't distinguish "new upstream event" from "site intentionally removed this one." This is the same tradeoff `Config.nmis` merging has technically always carried, but it's a *new* exposure for `Events.nmis` specifically, since — unlike `Config.nmis`, which every site has had since install — many sites are only just now getting a live copy of `Events.nmis` for the first time because of this ticket. Deliberately not coded around: constraining the merge to "only add sub-keys of entries that already exist" would defeat the actual goal of round 6, a genuinely new event type added in some future NMIS release would then never reach any existing customer at all. Recorded here as the accepted tradeoff instead, matching how `Config.nmis` merging has always worked.

**Test coverage added**: `test/t_updateconfig.pl` gained a section that runs the real `installer_hooks/10-postcopy-confmerges` shell script directly (not just `admin/updateconfig.pl`), against a fresh miniature install tree, proving both cases — a site with no `conf/Events.nmis` gets nothing created, a site that already has one still gets missing keys merged in. Running the *hook itself* was previously untested; only the generic, unrelated merge tool it calls was.

**Test hygiene fixes found along the way**: the same review found `test/t_updateconfig.pl`'s calls to `admin/updateconfig.pl` were invoking the real checkout copy directly, whose own config loading resolves relative to its own script location — meaning the test was reading and, in one case, writing into the *real* surrounding install's `conf/` and `var/` directories as a side effect, unrelated to whatever the test was actually asserting on. Fixed by running an isolated copy of the script from inside the test's own temp directory instead (with `<nmis_base>` patched in its own `conf-default/Config.nmis` copy, since that value is hardcoded to the real checkout's absolute path and would otherwise silently point right back at it). A separate, unrelated hygiene issue in `test/t_operational_status.pl`'s "Fix 1b" was also fixed: it mutated the shared, cached hashref `NMISNG::Util::loadTable` returns, rather than a copy, which could leak a synthetic test event into later `Events.nmis` loads in the same process.
